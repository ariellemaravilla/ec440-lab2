---- ALGORITHMS ----

>> A2: Briefly describe what happens in a call to timer_sleep(),
>> including the effects of the timer interrupt handler.

In a call to timer_sleep():
- timer_sleep(ticks) calculates the wake-up time as current tick + ticks.
- Interrupts are disabled to prevent race conditions while modifying shared data.
- The thread’s wake_tick field is set to the computed wake time.
- The thread is inserted into the global sleeping_list, kept sorted by wake_tick.
- The thread calls thread_block() to stop running until it is reawakened.
- timer_interrupt() runs at each tick, increments the global tick counter, and checks the front of sleeping_list.
- Threads whose wake_tick are less than or equal to the current time are removed from the list and unblocked using thread_unblock().




>> A3: What steps are taken to minimize the amount of time spent in
>> the timer interrupt handler?

- The sleeping_list is kept sorted by wake_tick when threads are inserted.
- In the interrupt handler, the list is ordered such that the earliest wake time is in the front. Only the front of the list is checked, rather than scanning every sleeping thread. 
- Once it finds a thread with a wake_tick greater than the current time, the loop breaks immediately, ensuring that the handler only performs minimal work each tick and avoids unnecessary iterations.

---- SYNCHRONIZATION ----

>> A4: How are race conditions avoided when multiple threads call
>> timer_sleep() simultaneously?

Interrupts are disabled before modifying shared data (intr_disable()), creating a short section of code that only one thread can run at a time.

This prevents the CPU from switching to another thread while the current one sets its wake_tick, adds itself to the sleeping_list, and calls thread_block().

Because interrupts are off, no other thread or interrupt can access sleeping_list during these steps. Also, timer_ticks() safely reads the global tick by disabling and re-enabling interrupts internally.



>> A5: How are race conditions avoided when a timer interrupt occurs
>> during a call to timer_sleep()?

The thread disables interrupts before changing shared data in timer_sleep(), so the timer interrupt can’t run in the middle of those updates.

The timer interrupt handler itself also runs with interrupts turned off by default, meaning it can safely check and remove threads from the sleeping_list without interference.

Because both timer_sleep() and timer_interrupt() only access the sleeping_list when interrupts are disabled, they never run at the same time, preventing race conditions.





---- RATIONALE ----

>> A6: Why did you choose this design?  In what ways is it superior to
>> another design you considered?


There were two approaches that were considered before the final implementation. One idea was to have a dedicated “timer daemon” thread run in the background, waking up every few ticks to scan through sleeping threads and unblock any whose time has arrived. This avoids doing the work in the interrupt handler but the response time is less precise as threads might wake slightly late

Another idea was to have each thread manage its own small queue for wake-up time and register itself with a global timer notifier. The timer interrupt then checks all threads’ wake flags individually instead of a single ordered list. This would be functionally correct but the interrupt handler must iterate over all threads (and not just sleepers), making it slower as thread count grows.

So while the first alternative sacrifices efficiency for simplicity and the second sacrifices efficiency for over-complexity, the final implementation keeps all sleeping threads in a single sorted list and wakes them directly from the interrupt handler, it avoids extra context switches, minimizes per-tick work, and provides precise, immediate wake-ups without added overhead.

>> B4: Describe the sequence of events when a call to lock_acquire()
>> causes a priority donation.  How is nested donation handled?
* 1. Thread T tries to acquire the lock held by H 
* 2. T sets T->waiting_on = lock and will call thread_donate_chain(T)
* 3. Donation will propogate
	-> if H has lower priority, raise it
	-> if H is waiting on another lock, continue up the chain 
* 4. Once lock becomes free, T will wake and clear on waiting_on. This will add the lock to held_locks and will then be recomputed for priority using thread_refresh_priority.
--> works because nested donations use chain traversal walks through holder->waiting_on on repeat.

>> B5: Describe the sequence of events when lock_release() is called
>> on a lock that a higher-priority thread is waiting for.
* 1. The releasing thread removes the lock from held_locks
* 2. It will then clear lock->holder 
* 3. Calls sema_up() to wake the highest-priority waiter
* 4. It will then call thread_refresh_priority() to then revert the priority back to the base priority or the max using the remaining held locks
* 5. If another thread has a higher priority, it will now use the CPU

>> C3: Did any ambiguities in the scheduler specification make values
>> in the table uncertain?  If so, what rule did you use to resolve
>> them?  Does this match the behavior of your scheduler?

The main ambiguity was what happens when multiple threads have the same priority. I used round-robin ordering for ties,  if threads have equal
priority, I pick the one that's been waiting longest in the ready queue. This happens naturally with list_push_back() when inserting into ready_list.
My scheduler matches this because I don't sort the ready list, I just append to it and let the highest priority thread run first.

>> C4: How is the way you divided the cost of scheduling between code
>> inside and outside interrupt context likely to affect performance?

I do most of the work in the timer interrupt (thread_tick), which runs every tick. Every tick I increment recent_cpu for the running thread.
Every 4 ticks I recalculate all thread priorities. Every second (100 ticks) I update load_avg and recent_cpu for all threads and this is pretty expensive
because I'm iterating through all threads multiple times, but it has to be done in interrupt context to keep the scheduler accurate. 
With many threads, these calculations could take a while and delay other interrupts. 

---- RATIONALE ----

>> C5: Briefly critique your design, pointing out advantages and
>> disadvantages in your design choices.  If you were to have extra
>> time to work on this part of the project, how might you choose to
>> refine or improve your design?

Advantages: My implementation is pretty straightforward and follows the formulas from the spec exactly. Using fixed-point macros made the math readable and I didn't have to worry about floating-point in the kernel.
The thread_mlfqs flag lets me cleanly switch between priority donation and MLFQS without breaking scheduler.

Disadvantages: The biggest issue is performance. I iterate through all threads every 4 ticks for priority updates and every 100 ticks for
recent_cpu updates. With hundreds of threads this would be really slow i feel.

If I had more time I'd  separate ready queues for each priority level (like the real 4.4BSD scheduler) so I wouldn't have to search for the highest priority thread. 

>> C6: The assignment explains arithmetic for fixed-point math in
>> detail, but it leaves it open to you to implement it.  Why did you
>> decide to implement it the way you did?  If you created an
>> abstraction layer for fixed-point math, that is, an abstract data
>> type and/or a set of functions or macros to manipulate fixed-point
>> numbers, why did you do so?  If not, why not?

I made fixed-point.h with macros instead of functions because they're faster. I used 17.14 format (F = 16384) for enough precision without overflow. For multiply/divide I cast to int64_t temporarily to prevent overflow. 
I made separate macros for fixed-point operations (FP_MULT, FP_DIV) versus fixed-point with integers (FP_MULT_INT, FP_DIV_INT) since they need different shifts.

The abstraction made thread.c way more readable I could write "FP_DIV(recent_cpu, INT_TO_FP(4))" instead of raw bit shifts. Also made debugging easier.
