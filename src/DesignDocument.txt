>> B1: Copy here the declaration of each new or changed `struct' or
>> `struct' member, global or static variable, `typedef', or
>> enumeration.  Identify the purpose of each in 25 words or less.
* int base_priority
--> Track donation chains, true values of the threads
* struct list held_locks
--> Also track donation chains, lists the owned locks for refreshing
* struct lock *waiting_on
--> used for track donation chains and links all the donations

>> B2: Explain the data structure used to track priority donation.
>> Use ASCII art to diagram a nested donation.  (Alternately, submit a
>> .png file.)
--> I used a chained-based model 
* Each of the thread points to the lock that it is waiting on using (waiting_on struct) 
* Each lock also knows its current holder and the holder has a held_locks list which will allow the donations to cascade.
* Nested donation can be handled by walking the chain up to a depth of 8 

ASCII Diagram:
 * High(PRI=63) --> waits on Lock_A (held up by medium thread)
 * Medium(PRI=31) --> waits on Lock_B (help up by low thread) 
Chain:
 High -> Medium -> Low 
After Donation:
low.priority = 63
medium.priority = 63
high.priority = 63

---- ALGORITHMS ----

>> B3: How do you ensure that the highest priority thread waiting for
>> a lock, semaphore, or condition variable wakes up first? 
* I ensure this by making sure that before unblocking or signaling all the waiting lists (ready_list, sema->waiters, cond->waiters) are sorted by priority by using list_insert_ordered and list_sort

>> B4: Describe the sequence of events when a call to lock_acquire()
>> causes a priority donation.  How is nested donation handled?
* 1. Thread T tries to acquire the lock held by H 
* 2. T sets T->waiting_on = lock and will call thread_donate_chain(T)
* 3. Donation will propogate
	-> if H has lower priority, raise it
	-> if H is waiting on another lock, continue up the chain 
* 4. Once lock becomes free, T will wake and clear on waiting_on. This will add the lock to held_locks and will then be recomputed for priority using thread_refresh_priority.
--> works because nested donations use chain traversal walks through holder->waiting_on on repeat.

>> B5: Describe the sequence of events when lock_release() is called
>> on a lock that a higher-priority thread is waiting for.
* 1. The releasing thread removes the lock from held_locks
* 2. It will then clear lock->holder 
* 3. Calls sema_up() to wake the highest-priority waiter
* 4. It will then call thread_refresh_priority() to then revert the priority back to the base priority or the max using the remaining held locks
* 5. If another thread has a higher priority, it will now use the CPU 

---- SYNCHRONIZATION ----

>> B6: Describe a potential race in thread_set_priority() and explain
>> how your implementation avoids it.  Can you use a lock to avoid
>> this race?

A potential race that can occur is if a thread changes its base priority while donations are still active
--> Prevention: Disable interrupts using intr_disable() during priority change
--> the locks will not be able to safely prevent because donations itself manipulate locks and disabling it is way simplier and more atomic
